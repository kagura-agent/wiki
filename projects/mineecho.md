# MineEcho — Local-first Memory OS

**Repo**: [Health-Yang/MineEcho](https://github.com/Health-Yang/MineEcho) · 145⭐ · TypeScript/Electron · Source-available (not OSS — custom license)

## Overview

MineEcho is a desktop AI assistant framework (Electron app) built around four pillars: memory persistence, knowledge management, skill routing, and token cost control. It positions itself as "a RAG app that acts, an agent framework that remembers." The product ships as a Windows installer / macOS DMG with a local BFF (backend-for-frontend) server and a Vue-based console.

Architecture: monorepo with `apps/bff` (Express backend, SQLite), `apps/console` (Vue frontend), and a vendored OpenClaw Gateway runtime. The BFF handles all memory/knowledge/skill logic; the console is a chat workbench UI.

**Key observation**: MineEcho is primarily a **product** (desktop assistant app) rather than a **framework**. This matters — its architecture decisions optimize for single-user desktop UX, not for agent-to-agent or programmatic use.

## Architecture

```
apps/
  bff/src/
    memory/           # 3-tier memory + L0-L3 tree
    knowledge-base/   # Wiki++ with 4-channel retrieval
    skills/           # Skill registry + router
    tokenjuice/       # TokenLess output compression
    ai-apps/          # External AI app adapters
    chat/             # Context budget planner
    learning/         # Skill analytics, trajectory
    channels/         # Feishu, WeCom integrations
  console/            # Vue SPA
vendor/
  openclaw-gateway/   # Vendored OpenClaw Gateway (forked)
```

Storage: SQLite for memory tree + file-based Obsidian-compatible markdown for content. No external database dependency.

## Memory System (L0-L3)

### Three-tier runtime memory

1. **Working Memory** — In-memory only, last 20 messages, current session context, active skills. Cleared on session end.
2. **Short-term Memory** — Daily interactions, learned preferences, pending tasks. Persisted to localStorage (frontend) + API (backend). Resets daily.
3. **Long-term Memory** — User profile (work style, tech stack, domain expertise), skill usage patterns, knowledge graph, project history. File-based JSON per user.

### L0-L3 Memory Tree (hierarchical summarization)

This is the more interesting system, running alongside the 3-tier model:

- **L0**: Raw memory chunks. Each conversation turn / skill invocation / document import becomes a chunk (max 3000 tokens). Stored in SQLite + Obsidian-compatible .md files.
- **L1**: Daily summaries. Generated by LLM when L0 tokens for the day exceed `l0SealThreshold` (default 21,000 tokens = ~7 chunks). Each L1 targets ~500 tokens.
- **L2**: Weekly summaries. Merges ~7 L1 summaries. Target ~800 tokens.
- **L3**: Monthly summaries. Merges ~4 L2 summaries. Target ~1000 tokens.

**Seal trigger**: When today's L0 token count ≥ threshold, a 5-second debounced seal schedules L1 generation. There's no cron — it's purely volume-triggered.

**Auto-compression**: Quota-based. Default quotas: L0=200K tokens, L1=1M, L2=5M, L3=unlimited. When usage hits 80% of quota, a background compression queue enqueues jobs to summarize lower levels into higher ones. Low-importance chunks are compressed first.

**Recall**: Multi-signal scoring:
- Keyword matching (tokenized content vs query)
- Semantic scoring via `scoreSemanticMemory()` — custom token overlap with CJK n-gram expansion + semantic alias groups (hardcoded)
- Local vector similarity via `buildSemanticVector()` (tf-idf style, no external model)
- Embedding-enhanced reranking when embedding provider is configured
- Importance weighting + recency decay

**Memory Dream**: A "dreaming" process that analyzes L0 chunks to find themes (via regex pattern matching against 8 hardcoded categories), identify forgetting candidates (importance ≤ 0.2 or short acknowledgments), and generate open questions. Scheduled periodically.

**Memory-to-Knowledge Alignment**: Detects when memory content overlaps with knowledge base nodes and proposes "alignment candidates" — links between memory items and knowledge graph nodes, scored by label/description matching with conflict detection.

### Assessment

The L0-L3 hierarchy is a solid design for progressive memory compression. The volume-triggered seal (vs. time-based) is smart — it avoids empty summaries on quiet days. The quota system with background compression is well-thought-out for long-term use.

**Weaknesses**:
- Semantic recall is primitive — hardcoded alias groups, no learned associations. The `SEMANTIC_ALIASES` array is manually maintained.
- Entity extraction falls back to regex for English (capitalized words = entities). LLM extraction only for Chinese text > threshold.
- The "dream" mechanism is pattern-matching theater — 8 hardcoded regex rules don't constitute real insight generation.
- No cross-user memory. Single-user only.

## Wiki++ Knowledge System

### 4-Channel Retrieval

1. **Vector search** — Embedding-based similarity. Requires configured embedding provider (OpenAI, local model). Optional — system degrades gracefully.
2. **BM25** — Custom implementation with CJK n-gram tokenization (2-6 char grams), stopword filtering, frontmatter tag/title bonus (+10/+5 score). Standard BM25 formula (k1=1.5, b=0.75).
3. **Structured search** — Matches on frontmatter type, tags, title, heading, filename. Pure metadata scoring, no content analysis.
4. **Graph channel** — Queries knowledge graph nodes by label, traverses 1-2 hop neighbors, loads chunks from related files, re-scores with BM25. Graph nodes come from entity extraction during indexing.

**Fusion**: Reciprocal Rank Fusion (RRF, k=60) merges all channels. Top 5 results returned. No per-channel score threshold (removed — different channels have incomparable scales).

### Indexing Pipeline

Raw files (PDF, DOCX, PPTX, XLSX, HTML) → text extraction → chunking (markdown-aware) → wiki pages (AI-maintained summaries). Entity extraction populates a knowledge graph stored in a `GraphStore`. Optional LightRAG integration for external graph engines.

### Assessment

The 4-channel retrieval is the project's strongest technical contribution. RRF fusion is the right approach for heterogeneous retrieval channels. The BM25 implementation handles CJK text properly (n-gram tokenization instead of word segmentation — simpler but effective). The graph channel adds genuine value by surfacing contextually related content that pure semantic or keyword search would miss.

**Weaknesses**:
- Graph is populated by simple entity extraction (regex for English, LLM for Chinese). No relation type inference.
- No incremental re-indexing — uses file mtime cache, but full re-read on any change.
- Chunk cache is in-memory (`wikiChunksCache`), no persistence across restarts.

## TokenLess Compression (internally: "TokenJuice")

### Architecture

JSON-based rule system with three layers: builtin → user → project (higher overrides lower). Each rule specifies:
- **Match**: toolName, argv[0], argv patterns, command patterns
- **Filters**: skipPatterns (remove lines), keepPatterns (retain only matching lines)
- **Transforms**: stripAnsi, trimEmptyEdges, dedupeAdjacent, prettyPrintJson
- **Summarize**: head N + tail N lines (classic head/tail truncation)
- **Counters**: Regex-based line counting (e.g., count PASS/FAIL lines)
- **outputMatches**: Short-circuit patterns (if output matches, return canned message)
- **Failure handling**: Different head/tail for non-zero exit codes

### Built-in Rules (15 files)

```
cargo__build.json    cargo__test.json     docker__logs.json
docker__ps.json      document__docx.json  document__html.json
document__pdf.json   document__pptx.json  document__xlsx.json
generic__fallback.json  git__diff.json    git__log.json
git__status.json     npm__list.json       npm__test.json
```

### Pipeline

1. **Classify**: Match input against rules by toolName/argv/command patterns. Score confidence (0-1) based on specificity.
2. **Apply**: Run skip/keep filters → transforms → head/tail summarize → counters → format with facts.
3. **Select**: Compare compacted vs. passthrough text. Use passthrough if output is small enough (< `TINY_OUTPUT_MAX_CHARS`). File inspection commands (`cat`, `head`, `tail`, etc.) are never compacted.

### Comparison with Our TACO (`compress-output.sh`)

| Aspect | MineEcho TokenLess | Our TACO |
|--------|-------------------|----------|
| Implementation | TypeScript, JSON rules | Bash, regex |
| Rule format | Structured JSON with match/filter/transform | Inline regex per type |
| Extensibility | 3-layer overlay (builtin/user/project) | Single script |
| CJK support | N/A (tool output is typically English) | N/A |
| Classification | Multi-field matching with confidence scoring | `--type` flag or auto-detect |
| Compression method | skip/keep patterns + head/tail | Keep first 5 + last 10, regex middle |
| Metrics | Persistent local metrics (raw/reduced chars, family) | None |
| Coverage | 15 rules: git, npm, cargo, docker, documents | 5 types: npm, pip, git, test, build |
| Claimed savings | 20-85% depending on scenario | ~84% on test output |

**Assessment**: TokenLess is more sophisticated in its rule matching and extensibility, but the actual compression mechanism is fundamentally the same: regex-based line filtering + head/tail truncation. The JSON rule format is cleaner than inline regex. The 3-layer override system (project rules override user rules override builtin) is genuinely useful for customization. The metrics tracking is a nice touch.

Both are "TACO pattern" (arXiv:2604.19572) implementations — regex-based, zero LLM calls. Neither does semantic compression. TokenLess wraps it more formally.

## Skill Routing

### Registry

Skills come from three sources:
1. **Trigger index** — parsed from skill markdown files (like our SKILL.md)
2. **Custom skills** — user-imported via JSON/ZIP/.skill packages
3. **AI apps** — external apps (RAG services, workflow tools) registered as callable skills

Each skill has: id, name, description, triggers[], category, enabled flag. Triggers are auto-derived from name + description via CJK n-gram extraction + English word extraction.

### Routing Algorithm

Score = max(trigger × 0.9, name × 0.8, description × 0.75) + mode bonus

- **Trigger score**: Exact match → 1.0, prefix → 0.9, substring → 0.75+. Weighted by trigger length.
- **Name score**: Substring match → 0.65.
- **Description score**: Token overlap between query and description text. Max 0.6.
- **Mode bonus**: +0.05 if mode=auto and skill is enabled.

Minimum score threshold: 0.35. Top 3 candidates returned.

### Assessment

The routing is simple text matching — no embeddings, no learned routing. This is exactly our approach (pattern matching in system prompt). The trigger derivation from name+description is a nice automation.

**Weakness**: No learning from routing outcomes. A skill that's frequently selected but fails doesn't get demoted. The `skill-analytics.ts` module tracks usage patterns but doesn't feed back into routing scores.

## Comparison With Our Approach

| Dimension | MineEcho | Our System (Kagura/OpenClaw) |
|-----------|----------|------------------------------|
| **Memory** | L0-L3 tree + 3-tier runtime | `memory/YYYY-MM-DD.md` + `MEMORY.md` + `beliefs-candidates.md` |
| **Summarization trigger** | Volume-based (token threshold) | Manual curation (daily-review cron) |
| **Memory retrieval** | Multi-signal scoring + embedding rerank | `memory_search` semantic search + file read |
| **Knowledge** | Wiki++ with 4-channel retrieval + graph | `wiki/` with memex (slug-based, backlinks, semantic search) |
| **Graph** | Entity-extracted knowledge graph | Backlinks in memex (simpler but functional) |
| **Compression** | TokenLess (JSON rules, 15 types, metrics) | TACO `compress-output.sh` (bash, 5 types) |
| **Skill routing** | Text-match scoring (trigger/name/desc) | System prompt pattern matching (SKILL.md) |
| **Architecture** | Electron desktop app, SQLite, single-user | Server-based gateway, multi-agent, file-based |
| **LLM integration** | Generic provider abstraction | OpenClaw gateway with provider routing |
| **Channel support** | Feishu, WeCom | Discord, Feishu, WhatsApp, Telegram |

### What They Do Better

1. **Structured memory hierarchy**: The L0-L3 tree with automatic volume-triggered summarization is more systematic than our flat daily files + manual curation. Progressive compression with configurable fanout ratios is well-designed.

2. **4-channel knowledge retrieval**: RRF fusion of vector + BM25 + structured + graph is genuinely stronger than our single-channel memex semantic search. The graph channel adds real value.

3. **TokenLess metrics**: Tracking compression ratios per tool family over time is useful for optimization. We have no equivalent.

4. **Memory-Knowledge alignment**: The explicit bridge between "things I remember" and "things I know" is a concept we lack. Our beliefs-candidates pipeline is similar in spirit but manual.

### What We Do Better

1. **Agent autonomy**: We have self-governance (DNA self-modification, beliefs pipeline, nudge hooks). MineEcho is a tool, not an agent.

2. **Multi-agent architecture**: Subagents, FlowForge workflows, team-lead coordination. MineEcho is single-agent.

3. **Memory curation quality**: Our manually curated MEMORY.md + beliefs-candidates pipeline produces higher-signal long-term memory than automated LLM summarization. LLM summaries lose nuance.

4. **Skill execution**: Our skills actually execute (shell commands, API calls, browser automation). MineEcho skills are routing targets — the actual execution is delegated to the chat completion.

5. **Real-world battle-testing**: Our systems run in production across multiple channels with real daily use. MineEcho is early-stage (v0.1.0).

## Key Takeaways

### Worth adopting/adapting

1. **Volume-triggered summarization**: Instead of our time-based daily review, consider summarizing when a day's memory exceeds a token threshold. Avoids empty/thin summaries.

2. **Compression metrics**: Add tracking to our `compress-output.sh` — log raw/reduced chars per invocation type. Cheap to implement, useful for tuning.

3. **Multi-channel knowledge retrieval**: Consider adding BM25 as a second channel to memex's semantic search. RRF fusion is simple and effective.

4. **Automatic trigger derivation**: Auto-extracting triggers from skill name+description could reduce maintenance of our SKILL.md trigger lists.

### Not worth adopting

1. **The full L0-L3 tree**: Our flat file system with manual curation is simpler and produces better-quality long-term memory. The summarization chain (daily→weekly→monthly) loses information at each level.

2. **Memory Dream**: Pattern-matching theater. Our nudge-based reflection is more grounded in actual behavioral signals.

3. **The desktop app architecture**: We're server-based and multi-agent. Different design space entirely.

## Criticisms / Limitations

1. **License ambiguity**: Claims "source-available" but no standard license file visible. The README says "SEE LICENSE IN LICENSE" but the actual terms are unclear. Not truly open-source.

2. **Zero issues/PRs**: Despite 145 stars, there are 0 issues. This suggests either very early release, no real user community, or issues are managed elsewhere.

3. **Hardcoded Chinese bias**: Semantic aliases, dream themes, conflict keywords are all in Chinese. The system would need significant rework for non-Chinese users.

4. **Vendored OpenClaw**: Ships a forked OpenClaw Gateway as a vendor dependency. This is a maintenance liability and raises questions about upstream contribution.

5. **Entity extraction quality**: Falls back to "capitalized words are entities" for English. This is barely above random.

6. **No real graph reasoning**: The knowledge graph stores entities and edges but does no graph reasoning (no path finding, no inference, no graph neural networks). It's a glorified adjacency list used for neighbor lookup.

7. **"15 reducer rules" marketing**: The README claims "15 built-in reducer rules" but several are document type rules (docx, html, pdf, pptx, xlsx) that just do head/tail on extracted text. The actual tool-specific rules (git, npm, cargo, docker) are 9.

8. **Scale concerns**: In-memory chunk cache, synchronous BM25 over all chunks, full file re-read on any change. This won't scale to large knowledge bases.
